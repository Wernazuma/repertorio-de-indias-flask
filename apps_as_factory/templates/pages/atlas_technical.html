Technical Methodology

The technical implementation of HGIS de las Indias is a response to the particular challenge of modelling colonial space, where boundaries were defined by ink rather than trigonometric measurement and had different meanings than today.

1. The atomic foundation: Least Common Geometry

The spatial core of the system is built on Least Common Geometry (LCG), an approach originally developed for the Belgian National HGIS. In a standard GIS, researchers create separate layers for different years or administrative branches, which creates a problem when changes must be made in a boundary, which then needs to be repaired for every layer and year separately.

The LCG method divides the entire Spanish American continent into a single set of non-overlapping polygons that serve as the spatial atoms of the system. Each LCG polygon obeys one rule: it must encompass an area that shares exactly the same administrative affiliations across all reconstructed levels, throughout the entire period.

If a territory belonged to the same civil district, intendancy and audiencia as its neighbour but fell under a different Bishopric, it had to become its own LCG polygon. If a small area — a cattle ranch, say — was transferred to a different jurisdiction in 1750, a new polygon was created to reflect that change. The system can therefore generate a clean, coherent map for any moment in time simply by joining these atomic polygons through a relational table.

2. Spatiotemporal modelling: the entity–instance concept

To handle the fluid nature of colonial history, the project separates the permanent identity of a place from its qualitative attributes through an entity–instance model.

  • Entities — every place or territory carries a stable Entity ID. The “Province of Chiapas” keeps the same ID (PRGUCH00) regardless of how its borders or official title changed over a century.
  • Instances — the qualitative “embodiments” of an entity at specific points in time. Arizpe remains the same entity, but its instances track its shifting status: from a mission (1701–1782) to a diocesan see (1783–1808), and from a town (1701–1780) to a city (1781–1808).

This separation lets researchers track institutional evolution (a corregimiento becoming a subdelegación) and spatial evolution (the “footprint” of a territory) as independent variables, reconnected only during the final output process. It also accommodates the historical custom of referring to those institutions as the same thing — “the province of Chiapas”, “the settlement Arizpe in Sonora”.

3. The hierarchical architecture: the 13 levels

Colonial administration was not a neat, single hierarchy. It consisted of overlapping and sometimes contradictory branches — civil, military, and ecclesiastical. And bottom up, municipal institutions — indigenous and Spanish — integrated into, mingled with, substituted, and competed with crown institutions. To capture this vernacular logic, the project reconstructs space across 13 levels (see the historical methodology):

  • Superior government — viceroyalties and independent captaincies-general.
  • Judicial / administrative — audiencias, intendencies, and three interpretations of “province” (major, regular, minor) to account for varying historical definitions and regional constellations.
  • Larger and smaller districts — jurisdicciones and partidos.
  • Ecclesiastical — archdioceses and dioceses.
  • Special categories — señoríos, frontier and uncontrolled territories, and foreign domains.

This multi-level approach lets the project represent the Viceroyalty of Peru in its broad definition — including the autonomous kingdoms of Chile and New Granada — at one level, while showing its narrower effective administration at another.

4. The relational database engine

The data is managed in a relational database management system, using several critical table types to connect time, space, and qualitative data:

  1. Entity and instance tables — the stable IDs and chronological attributes of every settlement and territory.
  2. Particle tables — settlement instances are themselves built from particle tables, each storing one strand of development: church hierarchy, name, location, settlement type, municipal institutions. These are then computed into the places instance table under a single chronology.
  3. LCG relation tables — the most abstract but most vital: they define which LCG polygons belonged to which Entity ID, at what time, for each of the 13 levels.
  4. Source table — every datum is linked to a Source ID, so the provenance of every point — census, diocesan visit, manuscript map — stays transparent and trackable. This, of course, has its limitations, as often enough different sources were weighed against or supplemented each other. In this case, we put the inital, or "sparking", source in the table

5. The Python automation workflow

A series of specialised Python scripts turns these relational tables into usable geographic files:

  1. Coordinate and metadata tagging — scripts add coordinates and “generic” (ahistorical) regional tags to entities, to assist disambiguation.
  2. Dumpfile creation — a script amalgamates the entity and instance tables into a single large dumpfile, updating start and end years into a consolidated timeline of qualitative changes.
  3. Spatial joins and SQL queries — the script joins the LCG polygons to the dumpfile on the IDs.
  4. The dissolve operation — the cartographic engine of the project: all LCG polygons sharing the same attributes for a given year and level have their internal boundaries dissolved, yielding one clean polygon per administrative unit (e.g. the “Audiencia of Mexico in 1750”).
  5. Temporal snapshot generation — the workflow generates one feature class for every level and every year: 12 levels × 108 years, plus 44 for the intendencia level, which exists only for part of the period — 1,340 in all.
  6. Optimisation for stability — an iterative script finds periods in which an entity’s geometry, type, and ID stayed stable and merges those yearly snapshots into a single spatiotemporal object with a broad start/end date, cutting the size of the resulting database dramatically.

6. Publication, accessibility, and repositories

The project’s goal is to function as a domain infrastructure for the scientific community. The data is therefore published through several channels:

  • Yale Dataverse — a mirror and repository for follow-up initiatives such as HGIS-Indias 2.0 and ARCA.
  • WebGIS apps — interactive applications with a time slider and toggleable layers, showing how missions, cities, and borders shifted between 1701 and 1808.
  • Encyclopedia — every entity has a landing page with its institutional history, lists of officials, and links to primary sources, functioning as an evolving historical-geographical dictionary. In the original project this was served as a DokuWiki resource; it has now been replaced by a different architecture within ARCA.
  • Harvard Dataverse — the original project’s repository: Python code, the original relational tables, and the processed shapefiles. No longer updated.

By assigning stable IDs to every historical place and territory, the project lets external researchers link their own socioeconomic data to this spatial framework. Any researcher can prepare a simple spreadsheet, upload it to ARCA, transform and match it against HGIS-Indias, and receive a shapefile in return — bridging the gap between tabular historical data and the historical geographical container units.
